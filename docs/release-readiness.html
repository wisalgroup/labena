Release readiness

This repository is distributed as a modular Go application template. The support policy defines latest-release maintenance, compatibility and verification scope. The adoption guide explains module renaming and updates for customized applications. The following gates distinguish verified behavior from remaining release work; a passing working-copy check is not a published release.

Verification matrix#

Capability Required evidence / current gate
Go behavior and lifecycle Fast CI race tests and vet with the go.mod toolchain
Commands and examples CI builds cmd and examples packages
PostgreSQL module queries and migrations Required disposable PostgreSQL integration job
Asynq, Redis cache and rate limits Required disposable Redis integration job
GoChannel Local integration tests; explicitly ephemeral, not durable delivery
HTTP contract and docs Live OpenAPI contract tests, compiled guide examples, and regenerated documentation site
Reachable dependency vulnerabilities Pinned govulncheck tool; advisory database remains current
Generic MySQL, Redis Cluster, cloud storage Not required core CI; validate separately before claiming support
Live Google sign-in, SMTP providers Local/unit coverage does not establish live provider compatibility

Build a local release bundle#

The same deployments/Dockerfile serves Tilt, Compose and release verification. Its Go builder is pinned by digest, refuses automatic toolchain downloads, verifies module checksums and builds with readonly dependencies. The non-root runtime contains the four application commands (app, cli, worker and scheduler), CA certificates and the project and Go licenses. Time-zone data is embedded; there is no shell or package manager. Keep /tmp writable and mount writable storage when using file logs or local media. Select configuration explicitly, including APP_ENV_FILE='' in managed deployments. Use HTTP probes rather than shell probes; run /app/cli directly for operator commands.

From a stable checkout, with Docker, Git, Go and shasum available:

./scripts/build-release.sh build/release-candidate linux/amd64
# Use linux/arm64 for an ARM deployment. The output directory must be new.

The build command requires a clean checkout with a version tag pointing at HEAD (for example v0.1.0) and does not publish anything. It injects that version and commit into all four binaries. Local builds without those arguments report dev. It saves:

  • app, cli, worker, scheduler and binaries.sha256;
  • image identity/configuration and each binary's embedded build/module information;
  • source-file checksums, Git revision, version.txt and working-tree status;
  • the full selected module graph, target-specific license report and copied notices.

The pinned license tool runs on the host while inspecting the selected Linux target. Keep notices with any binary/image distribution; the application image itself only contains project and Go notices. Review the report and its warnings, including files the scanner cannot inspect. The module path is github.com/wisalgroup/labena; while the upstream repository is private, unauthenticated tools cannot resolve its source/license URL. Record the upstream repository/tag and retain the local project license in the release evidence. Independently publishing importable Go packages would require accessible source and a separate API support declaration. License generation does not establish provider compatibility or expand the support policy. Tools and evidence belong to this local bundle, not the app's runtime or go.mod.

Use the immutable identity in image.id for subsequent tagging/export. Keep the bundle with the final published digest, test results and release notes. A local image ID is not a registry publication or signature. Repeat the build from the same source and toolchain, then compare binaries.sha256. Matching binaries do not imply byte-identical OCI archives; image metadata and exporter settings also affect archive identity. Before publication, require a clean tagged checkout. A dirty checkout's Git revision alone cannot identify what was tested; source.sha256 records the actual build inputs.

How to read the recorded evidence#

The dated sections below preserve historical verification. They describe the source and fixtures tested at that time, including behavior that may since have changed. They are not certification of the current working tree, current provider compatibility, or current vulnerability status.

For a new release candidate, create a new evidence record rather than replacing old checksums or silently carrying forward earlier passes. Record the commit/tag, source checksums, toolchain, architecture, backend versions, commands, results, skips, and operational limitations. The testing guide gives the repeatable core gate; deployment-specific recovery and provider checks remain separate.

Candidate hardening verification on 2026-10-18#

The local v0.1.0 candidate was checked with Go 1.27.2 and disposable PostgreSQL 17 and standalone Redis 7. The release bundle records its exact source revision, version and artifact identities; this source record does not announce publication.

No schema or task-payload migration is required for these hardening fixes. Live provider compatibility, production ingress configuration, sustained load, disaster recovery and the GitHub reporting channel still require deployment- or publication-specific evidence. This local gate does not establish those outcomes.

The temporary namespace ran as UID/GID 10001 with a read-only root filesystem, no service-account token, dropped capabilities, writable temporary/local-storage volumes and separate startup, liveness and dependency-readiness probes. Authentication, mail, push, scheduling and external providers were disabled for that fixture. Existing integration checks cover authentication independently.

The source scan and compiled Linux application scan both passed; that result is dated, not a permanent vulnerability guarantee. The cluster's kubectl exec transport still fails with an HTTP/HTTPS mismatch. HTTP exercises used the Kubernetes API proxy; operator commands used Docker against only the test container. No cluster settings were changed. This does not certify kubectl exec or port forwarding as healthy.

Restore used stopped producers/workers and a local object snapshot with no concurrent writers. The restore target used a separate database on the disposable PostgreSQL instance and a new Redis container. It was a Docker process, not a Kubernetes rollout. No production RTO/RPO, sustained-load drain, live provider delivery or historical-release upgrade guarantee was measured.

Run scripts/verify-integration.sh with all four test connection settings from .github/workflows/verify.yml. Missing or empty settings fail before tests run. Credentials must point to disposable services. PostgreSQL and Redis are the required matrix; unrelated optional suites can still report skips. A successful fast job alone is not sufficient for release.

Platform harmonization verification — 2026-10-11#

After the release-bundle exercise above, the harmonization changes passed the full race-enabled PostgreSQL/Redis integration gate, vet, command/example builds, focused regression checks, the shared Linux AMD64 Docker image build and the documentation builder. A second site build produced identical output. The image was built locally; no registry publication or Linux AMD64 runtime/load check was performed in this pass. The 51 published URLs, API schema, migrations, dependency versions and configuration profiles are retained. The pinned vulnerability scan again found no reachable or imported-package findings; four module-only advisories remain. No external provider delivery was attempted.

Regression coverage now includes safe HTTP diagnostics, transaction-effect guards, bounded SMTP attachment reads and cleanup, selected configuration validation, central subscription maintenance and retry-cycle diagnostics. Existing tests cover active HTTP, queue and subscriber drain; no new Kubernetes termination, sustained production load or disaster-recovery measurement was made for this patch.

Existing installations must deploy pruning-capable workers before enabling the new hourly schedule; see scheduling. Mail's aggregate attachment limit defaults to 20 MiB; see mail for ownership and retry semantics. Standalone named storage uses configuration selection plus storage.Open. The previous binary hashes and release bundle above identify the earlier source, not this patch. Regenerate the bundle before publication.

Before publication#

  • Record the upstream repository URL and publish the selected template adoption model, module-renaming instructions and support policy.
  • Enable GitHub private vulnerability reporting, verify the reporting entry point and assign report monitoring to the repository owner or a delegated maintainer; update the pending setup status in SECURITY.md only after verification.
  • Publish release notes covering fixes, compatibility changes and concrete update steps according to the release-note contract.
  • Record a tagged source revision, toolchain, dependency inventory and final license review, including non-Go runtime inputs such as the CA certificate bundle.
  • Retain release bundles, notices and checksums; verify each published architecture.
  • Run fresh installation tests. For later releases, state and test the supported upgrade starting points, including retained schema and queued work. This evidence does not promise automatic merging of customized application source.
  • Rehearse database/Redis backup and restore and document measured recovery outcomes.
  • Exercise process termination and dependency outages in the actual deployment target.
  • Measure performance before advertising throughput, latency or resource claims.

The support policy applies to future published releases; no historical release upgrade evidence is implied by the dated checks above. Do not rewrite applied migrations in a deployed application; publish versioned upgrade notes for schema, configuration, task names, event contracts and public API changes. Adopters port fixes into their own source, following the update workflow.

CI validates code and configured test backends. It does not prove disaster recovery, cloud behavior, deployment security, exactly-once execution or lossless telemetry. Maintain this matrix when adding a driver or capability; an interface alone is not evidence that a replacement has the same guarantees.

Assemble the next release evidence#

Evidence Re-run or record for the candidate
Source identity Upstream repository URL, clean tagged revision, github.com/wisalgroup/labena module path, exact build inputs
Core behavior Race suite with all required PostgreSQL/Redis endpoints; inspect skips
Build and static checks Vet, commands/examples, target image, documentation checks
Public contract Live OpenAPI and schema/task/event/configuration compatibility notes
Operational behavior Active-work drain, dependency outage, restart/recovery on the target
Retained data Backup/restore rehearsal with measured loss/time and matched asset bytes
Dependencies Current reachable-vulnerability and license review
Distribution Checksums, notices, release notes, support/security contacts

A failure or an unperformed check remains explicit in the release record. “The interface supports a driver” and “this deployment was verified with that driver” are different statements. Publish only the support scope backed by the candidate's evidence. Continue with deployment and testing.
